# 🎯 C++ SDK 开发 AGENTS 规范（面向 Codex）

本文件用于约束 Codex 在本仓库中编写、重构、测试 C++ SDK 代码时的行为。
优先目标：**可维护、可发布、可验证、可追溯**。

---

## 1. 🌏 语言与输出规范（不可违反）

1. 与用户沟通、分析与结论必须使用中文。
2. 代码中的注释、日志、错误信息统一使用英文。
3. 命名优先遵循仓库既有风格；不自行引入新的命名体系。
4. 代码评审结论使用中文输出，必须包含风险与建议。

---

## 2. 🎯 核心工程原则

1. 质量第一：禁止提交占位实现（TODO/MVP stub/未完成分支）。
2. 先分析后编码：编码前先确认需求边界、影响范围和验证方案。
3. 最小必要改动：只改与目标直接相关的内容，避免顺手重构。
4. 可回归验证：每个功能改动必须给出可执行的验证方式。
5. 可追溯：说明关键设计决策、权衡与兼容性影响。

---

## 3. 🏗️ C++ SDK 专项约束

### 3.1 API/ABI 与兼容性

1. 未经明确要求，不得破坏公开 API/ABI。
2. 变更公共头文件时必须评估：
- 符号可见性
- 二进制兼容性
- 下游编译影响
3. 删除或修改接口时，不保留无意义兼容层；若必须兼容，写明生命周期。

### 3.2 错误处理

1. 跨边界（模块/进程/网络）必须显式处理错误。
2. 统一错误语义：错误码、异常、状态对象不可混乱叠加。
3. 异常安全至少满足基本保证；资源释放路径必须完整。

### 3.3 资源与内存

1. 优先 RAII，禁止裸 `new/delete` 泄漏风险实现。
2. 明确对象所有权：`unique_ptr/shared_ptr/reference/raw pointer` 语义清晰。
3. 禁止返回悬垂引用、悬垂指针或临时对象引用。

### 3.4 并发与线程安全

1. 明确线程模型：线程安全/线程不安全必须在接口注释中说明。
2. 共享状态需有一致同步策略（mutex/atomic/lock-free），不得混用失控。
3. 回调、事件、异步任务必须定义生命周期与取消策略。

### 3.5 性能与复杂度

1. 优先评估时间复杂度和空间复杂度。
2. 高频路径避免不必要拷贝与分配，必要时使用 `move` 语义。
3. IO、锁、系统调用等高成本操作应避免放在热路径中。

---

## 4. 🧪 测试与质量门禁

1. 改动行为必须补齐或更新单元测试。
2. 后台执行测试时单次命令不超过 60 秒，避免阻塞。
3. 至少完成以下验证链路（按需裁剪）：
- 构建：`cmake --build`
- 测试：`ctest` 或目标测试二进制
- 格式：`clang-format`（遵循仓库配置）
- 静态检查：`clang-tidy`（如项目已启用）
4. 如果存在无法执行的验证，必须明确写出原因与风险。

---

## 5. 🛠️ 工具与执行规范

1. 搜索优先 `rg`，其次 `grep`。
2. 语义级改动优先使用 Serena 工具：
- 检索：`find_symbol` / `find_referencing_symbols` / `get_symbols_overview`
- 编辑：`replace_symbol_body` / `insert_before_symbol` / `insert_after_symbol`
3. 命令中的文件路径使用双引号包裹。
4. 不使用破坏性命令回滚用户已有改动。

---

## 6. ⚠️ 高风险操作确认（必须）

以下操作前必须得到用户明确确认：

- 删除/移动文件或目录
- `git commit` / `git push` / `git reset --hard`
- 大规模批量替换
- 系统配置、权限、环境变量改动
- 数据库结构变更或删除操作
- 访问生产环境或发送敏感数据

确认模板：

⚠️ 危险操作检测！
操作类型：[具体操作]
影响范围：[详细说明]
风险评估：[潜在后果]

请确认是否继续？[是/确认/继续]

## 7. ✅ 执行检查清单

### 任务开始

- [ ] 读取 Serena memory（至少风格与完成检查相关）
- [ ] 确认需求边界、影响文件、验证方式
- [ ] 选择工具链与降级方案

### 编码前

- [ ] 完成结构化计划（6-10 步）
- [ ] 明确 API/ABI、线程安全、错误处理策略
- [ ] 确认是否需要同步更新文档/示例/测试

### 实施中

- [ ] 保持最小改动面，避免无关重构
- [ ] 记录关键决策和兼容性影响
- [ ] 处理边界条件与异常路径

### 完成后

- [ ] 构建与测试通过（或给出失败原因）
- [ ] 输出变更摘要 + 风险说明 + 下一步建议
- [ ] 将关键经验写入 Serena memory

---

## 8. 📦 交付输出要求

1. 先给结果，再给细节。
2. 必须包含：
- 修改文件列表
- 核心行为变化
- 验证命令与结果
- 已知风险与后续建议
3. 信息不足时先声明假设，不得伪造结果。
